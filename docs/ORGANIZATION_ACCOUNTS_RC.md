# Organization accounts repair candidate — 0.1.25+26

This is an implementation and repair release candidate. It does not establish Wave 2 acceptance or production readiness. PR #6 must remain Draft and unmerged. A fresh Wave 2 campaign starts only after the owner receives and approves the exact installer and its checksum.

## Implementation

- An organization is the existing `tenant_id`. Its companies and branches share one protected application Owner. A partial unique index permits one Owner per organization; a database trigger prevents deleting, disabling, moving or demoting that Owner.
- Fresh native Host setup asks for the Owner username, password and confirmation. It uses the existing protected first-administrator bootstrap and recovery witness, then configures the account through the Host API. Initialization is serialized and cannot overwrite an existing organization's identity.
- Owner authority comes from the protected user row on every Host request. It covers current and future registered branches and approved modules within that tenant, including the Owner's own module submissions. Package validation, transactional rules and tenant RLS still apply. Archived scopes do not remove the Owner's ability to manage their organization.
- Native Users and permissions screens expose usernames, password changes/resets, direct permissions, enable/disable, organization-wide access, branch selection and session revocation. Existing permission-group screens continue to create, edit, assign and remove multiple groups. Administrative privileges are delegated direct grants; groups remain business permission groups. Effective permissions are the union of groups and direct grants, without a separate per-user deny override.
- Delegated administrators cannot change the Owner's login, disable the Owner, revoke Owner devices or manufacture additional administrative privileges. Their own administrative grants can be revoked by the Owner.
- Password login extends the existing device credential store. It does not introduce JWTs or a second command authentication path. Normal application requests still resolve current credentials and permissions inside the Host transaction.
- Usernames are case-insensitive within an organization, 3–64 characters, using letters, numbers, `.`, `_`, `@` and `-`. Passwords require at least 15 characters, with a 1024-byte UTF-8 maximum. Host and offline verifiers use independently salted PBKDF2-HMAC-SHA256 with 600,000 iterations through `cryptography` 2.9.0. This work factor follows the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Passwords do not enter SQLite, command arguments, audit details or diagnostic logs.

## Upgrade and explicit Owner migration

1. Close Ventio before running the new unified Windows installer. Use the normal installer and its protected native upgrade bridge. Do not uninstall with the option to delete Host data. The installed database, existing identity records, local SQLite databases, installed modules and queued commands are retained.
2. Migration `042_organization_accounts.sql` adds columns, constraints and indexes. It does not automatically promote an existing administrator, replace an existing identity or rewrite original migration checksums. The upgrade bridge refreshes account, administration, enrollment and schema contracts under the existing recovery authority protocol. For the old critical-only Windows payload, the installer verifies omitted PostgreSQL runtime files against an embedded inventory derived from the SHA-256-verified official EDB 16.15-5 archive; it never adopts arbitrary unlisted installed files. The published experimental `037_extension_submitter_review.sql` and `038_initial_account_owner.sql` chain is recognized only by its exact reviewed checksums. Its ledger entries, existing Owner flag and business data are retained while the canonical Wave 2 migrations are applied; unknown variants fail closed. An existing verified Owner can use **Finish first Owner setup** to choose its password using its previously provisioned credential.
3. Existing organizations need an explicit local Owner operation. On the Host, open **Ventio Organization Owner setup and recovery** from the Start menu or native first-run/sign-in screen. Windows administrator authorization is required. The existing administrator-only local service pipe independently checks the caller; there is no network Owner recovery endpoint.
4. Choose the appropriate operation:
   - **INITIALIZE** creates a new organization and its first company, branch and independent Owner. It refuses existing organizations.
   - **BOOTSTRAP** creates a new independent Owner in an existing organization that has registered branches and no Owner. Existing accounts and organization data remain intact. This avoids needing an existing account ID.
   - **MIGRATE** explicitly promotes the named active account in an existing unowned organization. Its actor ID and data are retained. Use this only when that exact account should become Owner.
   - **RECOVER** resets the existing Owner's username/password while retaining its actor ID and ownership. It revokes previous Owner credentials and unused pairing codes.
5. The protected wizard returns an enrollment code valid for five minutes, together with the Host endpoint and certificate fingerprint when its published LAN information is available. In Ventio, choose **Connect Client** / **Enroll another account or organization**, verify the Host fingerprint, enroll, then sign in with the chosen organization username and password. This also works for the native application running on the Host itself.
6. In **Users and permissions**, the Owner configures ordinary and delegated administrator logins and permissions. Enroll each account/device through **Devices and enrollment**. An existing enrolled device must match the account and organization used at password sign-in. Changing the active account or organization uses explicit enrollment and does not delete old local records or queued commands.

Legacy credentials remain in the Host database during migration. Configuring an account password turns its old device credential into enrollment proof: that credential can no longer authorize normal application requests by itself. Until each legacy account is configured, disabled or revoked, its existing token authorization remains compatible with the previous Host contract. Complete the Owner bootstrap and review legacy accounts before acceptance testing.

PostgreSQL identities remain separate: the database's `ventio_owner` is a NOLOGIN service/migration role, not the Ventio application Owner. Application usernames/passwords never grant PostgreSQL administrative login or database-tool access. Runtime and scoped API identities retain restricted function capabilities and no direct identity-table DML. Owner recovery records its mode, affected actor, time, Windows administrator SID and an operation tag in the identity audit.

## Offline authorization and revocation limits

- First enrollment and the first password sign-in on a device require the online Host. The native Host and Client applications use the same organization credentials and authorization path.
- Successful password sign-in issues a normal Ventio credential with a maximum eight-hour lifetime, bounded further by enrollment expiry. Specific-branch enrollment ceilings remain in force; organization-wide access is an explicit Owner decision.
- An independently salted offline verifier and authorization metadata are kept in the existing platform secure-storage backend, separate from SQLite. Windows uses the existing native protected credential backend. Plaintext passwords are never persisted.
- Offline sign-in is explicit. Five failed offline password attempts block offline sign-in until an online login. Expiry and detected backward clock movement require online login. The running app locks at expiry and records a clock high-water mark in protected storage.
- A reachable Host's login denial clears cached offline authorization. Online requests always enforce current Host permissions, account state, device state, enrollment-parent revocation and password version. Password changes invalidate existing online sessions; disabling an account does not restore those sessions when it is re-enabled.
- A disconnected device cannot learn a new revocation immediately. Its previously granted local access can last until the eight-hour lease expires. Queued work stays provisional and is reauthorized by the Host on reconnect. The lease assumes a trustworthy device clock and OS account; restoring protected storage or altering the OS as a privileged local administrator is outside the offline trust boundary. There is no claim of instantaneous disconnected revocation or a tamper-proof hardware clock.
- Enrollment credentials retain the existing 30-day provisioning lifecycle. Expired or revoked enrollment requires re-enrollment or the existing approved credential maintenance flow. Password session rotation does not extend the eight-hour authorization lease.

Tests are limited to the changed account/Owner path, migration preservation, secure offline credential handling, affected native screens, local recovery pipe contracts, static analysis and Windows build/package checks.

Host and affected native static analysis passed, as did migration checksum and schema-profile checks. Other focused checks cover duplicate initialization, independent tenant Owners, Owner protection, Host/Client login, live permission changes, multiple groups, offline bounds and local recovery audit.

No full Wave 2 acceptance suite, multi-device campaign, or P001–P006 disaster-recovery test is authorized or executed for this delivery. Existing installed Host services and persistent databases on the development machine are not used as test fixtures.

Actual clean-machine installation, installed Host upgrade through the complete installer, interactive elevated recovery, disconnected multi-device convergence, clock manipulation across OS restarts, and customer-data migration require verification against the approved candidate. Automated component checks and package validation do not substitute for those installed behaviors. The candidate is unsigned unless release metadata explicitly states otherwise.
