# Extension Builder — Device-Local Foundation

## What is implemented

The Windows/Android Flutter client now opens on an Extension Builder workspace. It can create an extension draft; define operational DocTypes, typed fields, enum choices and relationships; generate stable namespaced permission keys; configure and reorder generated list columns and form fields; preview metadata-driven lists and forms; activate or disable a definition on the current device; and remove an extension only when it has no local records. Required fields stay visible in generated forms. Hidden optional values remain intact when an existing record is edited.

Active local DocTypes render generated list, search, filter, sort, detail, create and update screens. The form handles text, integer, decimal, boolean, date, date-time, enum and same-scope record references. Metadata, records and revisions persist in a separate SQLite database using WAL and `synchronous=FULL`. Local record updates use optimistic revision checks.

Persisted extension drafts can be exported as a bounded, declarative `ExtensionBundle` and atomically installed or upgraded in another local store. Bundles are limited to 1 MiB, 64 DocTypes and 100 fields per DocType; nested JSON has structural limits. The package contract rejects unknown metadata, executable commands/capabilities, scripts, SQL, UI code and out-of-namespace permissions or localization keys. A new install remains a draft until explicitly activated. Package version changes must be monotonic; schema updates preserve existing DocTypes and fields and allow only reviewed non-destructive changes supported by the local engine. Local export/import stays device-local unless the user explicitly sends or fetches the package through the authenticated Host flow.

Schema updates reject field removal, type or relation changes, enum value removal, making existing optional fields required, and adding required fields without a migration. A compatible update advances the extension patch version and records' schema version in one local transaction. Existing business values are preserved.

Each DocType can declare which of the built-in read, create and update operations it supports. The local engine rejects undeclared operations and the generated UI hides those actions. An extension can declare permission keys only inside its own namespace. These declarations do not create Host grants or authenticate a user; Host authorization remains a separate boundary. Definition content is parsed as JSON metadata. The client loads no extension-supplied Dart, SQL, JavaScript or scripts.

The persisted command queue has an authenticated Host HTTP transport. Credentials are kept behind a platform secure-storage backend contract, remote origins require HTTPS, and cleartext is limited to exact loopback origins. Requests have bounded time and response size, use bearer authentication, validate API and command IDs, refuse redirects, and use the platform TLS verifier. Only receipts returned by the Host transport resolve queued commands. `RETRY_LATER` preserves the same command ID for idempotent retry; transport failures leave work provisional. The queue handles both the original maintenance proof and generic extension record create/update commands.

## Authority and security boundary

`DRAFT`, `ACTIVE_LOCAL`, and `DISABLED_LOCAL` describe this device only. Local activation is not Host installation or approval. Shared records are queried from the Host only for an approved package and exact authenticated tenant/company/branch scope. The Builder checks the Host package digest against the locally installed declarative package before accepting query results. Local create/update commands remain provisional until a real Host receipt resolves them. A test fixture receipt cannot imply Host acceptance.

The app can now store a Host-issued credential in Windows/Android secure storage, discover the authenticated tenant and exact company/branch grants, and save a selected package-transfer scope. Credential provisioning is still a manual operator step; the app does not yet enroll devices or rotate credentials. Local preview records still use the sample workspace scope. SQLite queries and relationship checks include organization, company and branch IDs, but a user with access to the local device/database can bypass them. They are not a security boundary. Host authorization, exact role grants, row-level isolation and audited changes must be enforced by the Host before shared records are used.

The Host API defaults to `127.0.0.1` and rejects external listeners unless they use TLS and a persistent authenticator. The `local_host.dart` launcher accepts explicit interface and certificate/key paths for that mode. Protected private-file and recovery-witness operations have Linux and ACL-backed Windows implementations. The Windows ACL integration test passed on the development machine, but the complete Windows Host/PostgreSQL service and remote-device path has not been end-to-end verified. Remote certificate provisioning/rotation, device enrollment/pairing, credential rotation, and production service lifecycle remain incomplete. Client transport tests use local test servers; they do not establish secure connectivity to a real multi-device Host. Do not treat a configured listener as a production deployment until those pieces are tested together.

## Current limits

- Device-local extension dependencies support minimum compatible semantic versions (patch-only for `0.x`, same-major for `1.x` onward), activation order, cycle rejection and safe disable/remove checks. Host approval enforces compatible approved dependencies and monotonic releases. Package transfer through the Builder is manually initiated; background discovery and automatic upgrades are not implemented.
- Local permission keys are not tied to users or roles. The extension cannot grant itself authority, but a Host-controlled role editor is still needed.
- Only the built-in local data renderer is available. No user-defined executable operation or workflow DSL is included.
- Local search, filtering and sorting run in SQLite before the result limit is applied, so older matching records are not hidden by the page size. Searches use escaped `LIKE` predicates over JSON fields; the engine does not yet build indexes for those paths, so large datasets still need query-plan and indexing work before making scale claims.
- The local preview workspace still uses a fixed sample scope. Live records use the authenticated Host session's selected exact scope. The Host is authoritative; local caches and their scope labels do not provide an independent security boundary.
- Compatible metadata upgrades are deliberately additive. Destructive data transformations need a future reviewed, resumable Host migration protocol and offline-command upcasting.
- The Host persists validated candidates, supports exact-scope package submission and approved reads, and provides recovery-witness-protected local approval/revocation. The Builder now connects to these routes: it can submit a review candidate and fetch an approved package, verify the Host digest, and install it as a local draft. Operator approval remains a separate trusted Host action.
- Dynamic DocType pages query the Host's approved package and records using bounded filtering, sorting and paging; they enqueue create/update commands for later sync and reconcile Host acceptance, rejection, retry, and revision-conflict receipts into local state. Startup reconciliation also recovers records saved before a process interruption between local persistence and queue insertion.
- Conflict receipts preserve the local draft. The Builder can fetch one exact authenticated Host record, retain the Host snapshot separately, review values field by field, and submit a new command against the Host revision. The Host still performs the authoritative revision and permission checks; concurrent Host changes can produce another conflict. Shared package upgrades use the Host registry and the client only accepts additive schema updates supported by the local engine. Resumable destructive migrations and offline command upcasting are not available.
- The in-app Host flow stores credentials via the platform secure-storage contract and selects an exact granted branch scope. Device enrollment/pairing, credential rotation, automated package upgrades, and background sync remain incomplete; users initiate sync.
- Decimal fields in this generic local store are data fields; this does not implement exact-money rules or financial posting.
- The Host extension registry and dynamic record integration suites passed in CI against disposable PostgreSQL 16 for source commit `7f31ad7`. On 2026-10-24, the package approval and generic record integration also passed locally on Windows Dart against a disposable PostgreSQL 16 Docker container (33 assertions, including exact-record conflict review and scope isolation); the container was removed after the run. This does not represent a persistent or remotely reachable Host deployment. An Android API 37 x86_64 emulator was used for a device-local Builder and record lifecycle smoke; no Host was configured during that run, and no physical Android hardware was used.

- `flutter analyze`: passed with no issues.
- `flutter test`: all 60 client tests passed, including persistent SQLite reopen and migration, Host query scope/digest checks, exact-record query serialization, queued record updates, interrupted-save recovery, conflict snapshot isolation, field-level merge selection, explicit Host-version adoption, and phone-sized layouts.
- `dart format --output=none --set-exit-if-changed lib test`: passed with no formatting changes.
- Windows PowerShell and Ubuntu shell scaffolding generators ran successfully in their platform-specific CI jobs; fresh Windows and Android runner generation passed.
- Windows Release executable: built from the current source and remained alive for a five-second startup smoke; the UI was not manually inspected during that smoke.
- Host API unit suite: 45 assertions passed. The package/record PostgreSQL integration also ran locally in a disposable container; the rest of the database and recovery integration matrix remains covered by CI.
- Extension package/PostgreSQL integration: 33 assertions passed locally on Windows Dart against a disposable PostgreSQL 16 container after applying all 16 migrations and the reviewed test security bootstrap. The test covered package approval, Host-authoritative records, exact-record retrieval, revisions, conflict rejection, scope isolation, and RLS. The temporary container was removed.
- Repeat the Windows integration with `pwsh -File scripts/test-extension-package-windows.ps1`; it uses an isolated database and cleans up its uniquely named container after success or failure.
- Windows ACL-backed private-file and recovery-witness checks passed on the development machine.
- Android Release APK: built from the current source (55.3 MB), installed and exercised on an Android API 37 x86_64 emulator. The smoke created two different local extensions and DocTypes, previewed a generated form, activated both locally, created records in both, edited a record, toggled local activation, and restarted the app to verify SQLite persistence. A metadata-only version change from `0.1.0` to `0.1.1` preserved the second extension's record; this did not exercise a package upgrade or schema migration. All records remained local-only because no authenticated Host was configured.
- Core executable suite: 58 passed, including declarative bundle validation, metadata bounds, exact-scope authorization and the strict create/update command envelope for generic extension records.
- Host API unit suite: 45 passed.
- PostgreSQL line-ending checksum test: passed without a database.
- Python schema/package checks and V1.2 contract tests: passed (20 unit tests).
- PostgreSQL adapter, Host package approval, dynamic record read/write and page-bound integration tests passed in CI against disposable PostgreSQL 16. All eight workflows passed for source commit `7f31ad7`. A local disposable-container run additionally passed the extension package and dynamic record integration on Windows. No existing Ventio database was used.

These results prove the local foundation and its tested behavior. The client now has tested Host read/query and queued write/reconciliation paths, and CI exercises the package/record database gateways against disposable PostgreSQL. The emulator run proves Android installation and the device-local workflow only; it does not prove physical-device behavior, live Windows Host deployment, multi-device operation, or production readiness.
