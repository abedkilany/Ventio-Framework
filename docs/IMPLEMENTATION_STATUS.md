# Implementation status

Current development continues on the independent `codex/extension-platform` branch. It keeps the original Ventio app, `main`, and tag `v0.2.0` unchanged. The product goal is a framework for building future extensions inside Ventio, not a prebuilt sales, accounting, inventory, purchasing, or manufacturing ERP.

The verification snapshot below reflects the latest local Windows full integration run. Android Host-sync evidence is recorded separately and was collected on the same development machine, not a separate LAN device. Bullets that describe earlier source states are historical evidence.

## Implemented

| Area | Current capability | Boundary |
| --- | --- | --- |
| Extension Builder | Creates and edits declarative extension packages, dependencies, DocTypes, typed fields including numeric and text-length bounds, references, validation, generated page title/icon/navigation order, list columns, form order, detail-page field order, operation declarations, and namespaced operation and field permission keys. On Windows and Android it can author the bounded migration operations `renameField` and `setDefault`, preview, export/import, submit for Host review, browse the scoped Host-approved registry, install by digest, activate, disable, and perform safe removal checks. New packages require platform API `0.3.0`; clients running `0.2.x` or earlier reject them. | Definitions contain metadata only. Generated navigation is one safe, generic record page per DocType; arbitrary page composition, custom widgets, routes, and scripts are not supported. Metadata cannot execute uploaded Dart, SQL, or scripts. Permission declarations do not grant Host authority. |
| Dynamic data and UI | SQLite persists extension metadata and records. Generic Flutter screens provide generated record lists, configurable page title/icon/order, create/edit forms, configurable list columns and field order, detail views, search, filter, sort, field validation, and reference selection. Older metadata without page settings or a detail layout receives stable defaults. The Host grants per-field read/write masks at the authenticated company/branch scope; protected values are omitted from records, unreadable fields cannot be searched/filtered/sorted, and update forms submit partial patches. Local schema v9 stores per-identity Host field masks and record projections alongside exact Host conflict snapshots. A newly learned read denial scrubs protected values from cached rows and conflict data. Host equality filters use a shared JSONB GIN index; a PostgreSQL plan assertion verifies it is available to the parameterized predicate. | Local SQLite is a cache/workspace, not a security boundary. A device offline before it learns about a later Host permission revocation cannot enforce that remote change. Type conversion, field deletion, constraint narrowing, tombstones, local search indexes, Host substring-search/sort indexes, and production-scale query tuning remain open. An unresolved local Host command blocks a data migration. The GIN index adds storage and write cost; migration 022 uses a transactional build and may need a scheduled maintenance window on a large database until online index-build support is added. |
| Host records and registry | The Host stores generic extension records and approved immutable packages in PostgreSQL. Restricted operator approval validates migration metadata and atomically applies the same bounded `renameField` and `setDefault` operations to tenant records before approving a release; each changed record receives a new Host revision. The generic Host also lists bounded package summaries, fetches selected approved versions, queries records, and accepts create/update commands. Record queries return Host-computed readable, writable and creatable field masks for the exact principal and scope. Search uses readable fields only; filters and sort on unreadable fields are denied. Updates merge partial patches with the locked Host row and reject unauthorized changes to protected fields. References resolve only within the same tenant, company, branch, module, and DocType. | Type conversion, field deletion, and constraint narrowing still fail closed. Only the highest approved release authorizes runtime record queries or new writes. Older approved versions remain downloadable history but return `UPGRADE_REQUIRED`; if the highest release is revoked, older releases return `EXTENSION_REVOKED` rather than becoming active again. Identical retries of already accepted commands still return their saved receipt. In-flight operations coordinate with approval/revocation. Offline command upcasting is not implemented, so clients must upgrade and resolve rejected drafts. This remains a disposable test database, not a persistent Host deployment. |
| Scope and permissions | Host authorization checks current user/device credentials, direct grants and tenant roles assigned to an exact company/branch pair, package approval, declared operation, expected revision, and the credential's provisioned permission ceiling. PostgreSQL RLS adds a separate database enforcement layer. The client obtains scope from an authenticated Host session instead of trusting a record form's scope. | Role management is available through the Host-connected Flutter role editor. Its reserved capability is granted directly by a trusted operator and cannot be delegated through a role. Device enrollment and a full organization hierarchy administration experience are not included. A local cache can be altered by someone with access to the device. |
| Offline queue | Dynamic create/update commands are durably queued with stable command IDs, retried through the authenticated Host transport, and reconciled from Host receipts. Accepted, retryable, rejected, and revision-conflict outcomes remain distinguishable. Before sending, the client validates the real Host session against the saved identity and scope, then checks every queued command against exact tenant/company/branch/actor/device values; a mismatch leaves the queue pending without recording an attempt. Conflict review fetches one authenticated Host record, preserves both snapshots, supports field-by-field value selection, and submits a new revision-checked command. Startup repairs the gap between SQLite record persistence and queue insertion after a process interruption. | Windows Host sync is exercised from an Android API 37 emulator to the Host's selected Windows network-interface address over TLS, including offline retry, two-identity stale-write conflict/review/merge, queue and record persistence after SQLite reopen, and read from a second identity. The two logical client databases run on one emulator; this does not validate two physical Android devices, a separate LAN client, or physical-device offline behavior. Local test fixtures are not Host evidence. |
| Host lifecycle/security | The production Host launcher starts without built-in business-command bindings; generic extension records use the approved metadata-backed engine. The Host API defaults to loopback HTTP for local development and supports explicitly configured TLS certificates on loopback or remote addresses. Non-loopback listeners require TLS, persistent authentication, and authoritative command/package/query components. The persistent Windows/Linux launcher uses a bounded runtime PostgreSQL pool (16, matching HTTP admission) and a separate 4-connection identity-administration pool; connection lifetime, session-use, query-count, connect, and query timeouts are capped. Shutdown drains admitted HTTP work before closing pools. Every lease still revalidates identity, authorization, RLS scope, and recovery admission; no permission cache is held in the pool. Protected credential and recovery-authority file operations have Linux and Windows-specific implementations. PostgreSQL recovery admission uses a protected generation and transaction-bound proof. Dynamic-extension RLS uses a transaction-, backend-, role- and exact-scope-bound HMAC authorization cache established by the trusted resolver; tampered or stale cache state fails closed. Identity and role row locks remain held for the transaction, so revocation cannot race accepted work. SQL, metadata, and package validation reject arbitrary executable behavior. The Flutter role editor works through the persistent Host when its restricted identity-admin connection and explicit Host-owned witness-write profile are configured. | The Windows Host process and restricted PostgreSQL logins are exercised together. A self-signed test certificate verifies HTTPS on the Windows network interface, default certificate rejection, and client success with an explicit trust anchor. An Android emulator also reached that Host address with default rejection and explicit certificate trust. No separate LAN device has been tested. External certificate provisioning, service installation/rotation, pool saturation telemetry, and production operations still need deployment evidence. |
| Platform builds | The runner preparation scripts generate Windows and Android runners. Local SQLite selects the native backend on Android/iOS and SQLite FFI on Windows/Linux/macOS. Core and Host remain separate Dart packages with database/filesystem abstractions rather than Flutter or OS-specific dependencies in Core. | Windows and Android are built and exercised. Linux, macOS and iOS backend selection is unit-tested but those runners are not generated by the current priority build scripts and have not been built or run. Linux FFI deployments also need the system SQLite library and a supported secure-storage/keyring service. Android was exercised on an API 37 x86_64 emulator, not physical hardware. |

## Remaining production gates

- Complete a real Windows Host deployment with PostgreSQL, protected recovery-authority provisioning, certificates, and remote Windows/Android credential enrollment. Current Host/client acceptance uses the Windows machine and an Android emulator reaching the Host over the Windows network-interface address; it is not a separate-device LAN deployment.
- Provision a user-controlled Android release signing key outside the repository and verify a distribution-signed APK before publication.
- Run the cross-device acceptance scenario through a LAN-reachable Host and separate devices: approve the locally demonstrated distinct extensions, synchronize actual records, exercise conflict/rejection and an extension upgrade without data loss, then verify on a second physical device.
- Exercise the Windows UI manually and install/run the APK on physical Android hardware.
- Validate the complete conflict/rejection and migration-refresh lifecycle against a live multi-device Host, including concurrent edits that advance the Host revision during user review. Current schema migrations only rename fields and set validated scalar defaults; resumable batches, type conversions, field deletion, and constraint narrowing still need a reviewed protocol.
- Add workload evidence for large Host/local datasets; the new Host GIN index covers equality filters only, while substring search, sort expressions, and local search remain unindexed. Query bounds protect request size but do not make an enterprise-scale latency guarantee. Migration 022 builds the index transactionally and may block writes during a large existing-table scan; use a maintenance window until online index-build support exists.
- Production recovery still requires rollback protection outside the shared database and witness rollback domain. Matching rollback of both artifacts cannot be detected by the current local freshness design.
