# Implementation status

Current work is on `codex/extension-platform` at source commit `c2e6891`. It keeps the original Ventio app, `main`, and tag `v0.2.0` unchanged. The product goal is a framework for building future extensions inside Ventio, not a prebuilt sales, accounting, inventory, purchasing, or manufacturing ERP.

## Implemented

| Area | Current capability | Boundary |
| --- | --- | --- |
| Extension Builder | Creates and edits declarative extension packages, dependencies, DocTypes, typed fields including numeric and text-length bounds, references, validation, list columns, form order, operation declarations, and namespaced permission keys. Supports preview, export/import, package review submission, browsing the scoped Host-approved registry, digest-verified installation, local activation, disable, and safe removal checks. | Definitions contain metadata only. They cannot execute uploaded Dart, SQL, scripts, or arbitrary UI code. Permission declarations do not grant Host authority. |
| Dynamic data and UI | SQLite persists extension metadata and records. Generated Flutter screens provide list, detail, create, edit, search, filter, sort, field validation, and reference selection without a page per DocType. Additive supported schema changes are guarded; record updates use local optimistic revisions. Local schema v5 retains an exact Host conflict snapshot separately from provisional values. Host equality filters use a shared JSONB GIN index; a PostgreSQL plan assertion verifies it is available to the parameterized predicate. | Local SQLite is a cache/workspace, not a security boundary. Destructive migrations, tombstones, local search indexes, Host substring-search/sort indexes, and production-scale query tuning remain open. The GIN index adds storage and write cost; migration 022 uses a transactional build, so an established large Host would need a scheduled maintenance window until online index-build support is added. |
| Host records and registry | The Host stores generic extension records and approved immutable packages in PostgreSQL. Operator approval rejects destructive schema updates until a reviewed migration protocol exists. Authenticated clients can list bounded package summaries, fetch one digest-verified version, query records, and submit generic create/update commands. References resolve only within the same tenant, company, branch, module, and DocType. | Core separately rejects missing targets and targets in another tenant, company, or branch. PostgreSQL integration separately rejects a target in another branch of the same company and another company at the same branch ID, without committing the invalid record. This remains a disposable test database, not a persistent Host deployment. |
| Scope and permissions | Host authorization checks current user/device credentials, direct grants and tenant roles assigned to an exact company/branch pair, package approval, declared operation, expected revision, and the credential's provisioned permission ceiling. PostgreSQL RLS adds a separate database enforcement layer. The client obtains scope from an authenticated Host session instead of trusting a record form's scope. | Role management is available through the Host-connected Flutter role editor. Its reserved capability is granted directly by a trusted operator and cannot be delegated through a role. Device enrollment and a full organization hierarchy administration experience are not included. A local cache can be altered by someone with access to the device. |
| Offline queue | Dynamic create/update commands are durably queued with stable command IDs, retried through the authenticated Host transport, and reconciled from Host receipts. Accepted, retryable, rejected, and revision-conflict outcomes remain distinguishable. Before sending, the client validates the real Host session against the saved identity and scope, then checks every queued command against exact tenant/company/branch/actor/device values; a mismatch leaves the queue pending without recording an attempt. Conflict review fetches one authenticated Host record, preserves both snapshots, supports field-by-field value selection, and submits a new revision-checked command. Startup repairs the gap between SQLite record persistence and queue insertion after a process interruption. | Windows Host sync is exercised from an Android API 37 emulator to the Host's selected Windows network-interface address over TLS, including offline retry, persisted receipt after SQLite reopen, and read from a second identity. This validates the emulator's route to the Windows interface, not a separate LAN device or physical-device offline trial. Local test fixtures are not Host evidence. |
| Host lifecycle/security | The production Host launcher starts without built-in business-command bindings; generic extension records use the approved metadata-backed engine. The Host API defaults to loopback HTTP for local development and supports explicitly configured TLS certificates on loopback or remote addresses. Non-loopback listeners require TLS, persistent authentication, and authoritative command/package/query components. Protected credential and recovery-authority file operations have Linux and Windows-specific implementations. PostgreSQL recovery admission uses a protected generation and transaction-bound proof; identity/history is no longer rehashed for each RLS row. SQL, metadata, and package validation reject arbitrary executable behavior. The Flutter role editor works through the persistent Host when its restricted identity-admin connection and explicit Host-owned witness-write profile are configured. | The Windows Host process and restricted PostgreSQL logins are exercised together. A self-signed test certificate verifies HTTPS on the Windows network interface, default certificate rejection, and client success with an explicit trust anchor. An Android emulator also reached that Host address with default rejection and explicit certificate trust. No separate LAN device has been tested. External certificate provisioning, service installation/rotation, and production operations still need deployment evidence. |
| Platform builds | The runner preparation scripts generate Windows and Android runners. Local SQLite selects the native backend on Android/iOS and SQLite FFI on Windows/Linux/macOS. Core and Host remain separate Dart packages with database/filesystem abstractions rather than Flutter or OS-specific dependencies in Core. | Windows and Android are built and exercised. Linux, macOS and iOS backend selection is unit-tested but those runners are not generated by the current priority build scripts and have not been built or run. Linux FFI deployments also need the system SQLite library and a supported secure-storage/keyring service. Android was exercised on an API 37 x86_64 emulator, not physical hardware. |

## Remaining production gates

- Complete a real Windows Host deployment with PostgreSQL, protected recovery-authority provisioning, certificates, and remote Windows/Android credential enrollment. Current Host/client acceptance uses the Windows machine and an Android emulator reaching the Host over the Windows network-interface address; it is not a separate-device LAN deployment.
- Provision a user-controlled Android release signing key outside the repository and verify a distribution-signed APK before publication.
- Run the cross-device acceptance scenario through a LAN-reachable Host and separate devices: approve the locally demonstrated distinct extensions, synchronize actual records, exercise conflict/rejection and an extension upgrade without data loss, then verify on a second physical device.
- Exercise the Windows UI manually and install/run the APK on physical Android hardware.
- Validate the complete conflict/rejection lifecycle against a live multi-device Host, including concurrent edits that advance the Host revision during user review. Reviewed resumable migrations for changes beyond the supported additive schema subset are still needed.
- Add workload evidence for large Host/local datasets; the new Host GIN index covers equality filters only, while substring search, sort expressions, and local search remain unindexed. Query bounds protect request size but do not make an enterprise-scale latency guarantee. Migration 022 builds the index transactionally and may block writes during a large existing-table scan; use a maintenance window until online index-build support exists.
- Production recovery still requires rollback protection outside the shared database and witness rollback domain. Matching rollback of both artifacts cannot be detected by the current local freshness design.
