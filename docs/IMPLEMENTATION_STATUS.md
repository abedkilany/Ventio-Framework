# Implementation status

Current work is on `codex/extension-platform`. It keeps the original Ventio app, `main`, and tag `v0.2.0` unchanged. The product goal is a framework for building future extensions inside Ventio, not a prebuilt sales, accounting, inventory, purchasing, or manufacturing ERP.

## Implemented

| Area | Current capability | Boundary |
| --- | --- | --- |
| Extension Builder | Creates and edits declarative extension packages, dependencies, DocTypes, typed fields, references, validation, list columns, form order, operation declarations, and namespaced permission keys. Supports preview, export/import, package review submission, Host-approved package installation, local activation, disable, and safe removal checks. | Definitions contain metadata only. They cannot execute uploaded Dart, SQL, scripts, or arbitrary UI code. Permission declarations do not grant Host authority. |
| Dynamic data and UI | SQLite persists extension metadata and records. Generated Flutter screens provide list, detail, create, edit, search, filter, sort, field validation, and reference selection without a page per DocType. Additive supported schema changes are guarded; record updates use local optimistic revisions. Local schema v5 retains an exact Host conflict snapshot separately from provisional values. | Local SQLite is a cache/workspace, not a security boundary. Destructive migrations, tombstones, broad query indexing, and production-scale query tuning remain open. |
| Host records | The Host stores generic extension records in PostgreSQL. Authenticated clients can query bounded pages or one exact record from an approved package and submit generic create/update commands. The client verifies the installed package digest against the Host-approved release before importing shared records. | The package approval and dynamic record integration passed locally on Windows against a disposable PostgreSQL 16 Docker container. This was an isolated test database, not a persistent Host deployment. |
| Scope and permissions | Host authorization checks current user/device credentials, direct grants and tenant roles assigned to an exact company/branch pair, package approval, declared operation, expected revision, and the credential's provisioned permission ceiling. PostgreSQL RLS adds a separate database enforcement layer. The client obtains scope from an authenticated Host session instead of trusting a record form's scope. | Role management is available through the Host-connected Flutter role editor. Its reserved capability is granted directly by a trusted operator and cannot be delegated through a role. Device enrollment and a full organization hierarchy administration experience are not included. A local cache can be altered by someone with access to the device. |
| Offline queue | Dynamic create/update commands are durably queued with stable command IDs, retried through the authenticated Host transport, and reconciled from Host receipts. Accepted, retryable, rejected, and revision-conflict outcomes remain distinguishable. Conflict review fetches one authenticated Host record, preserves both snapshots, supports field-by-field value selection, and submits a new revision-checked command. Startup repairs the gap between SQLite record persistence and queue insertion after a process interruption. | No live multi-device network deployment or physical-device offline/reconnect trial has been performed. Local test fixtures are not Host evidence. |
| Host lifecycle/security | The Host API defaults to loopback HTTP for local development and supports explicitly configured TLS certificates on loopback or remote addresses. Non-loopback listeners require TLS, persistent authentication, and authoritative command/package/query components. Protected credential and recovery-authority file operations have Linux and Windows-specific implementations. PostgreSQL recovery admission uses a protected generation and transaction-bound proof; identity/history is no longer rehashed for each RLS row. SQL, metadata, and package validation reject arbitrary executable behavior. The Flutter role editor works through the persistent Host when its restricted identity-admin connection and explicit Host-owned witness-write profile are configured. | The Windows Host process and restricted PostgreSQL logins are exercised together on loopback. A self-signed test certificate verifies HTTPS startup, default certificate rejection, and client success with an explicit trust anchor. A Host serving remote Windows/Android clients over a LAN has not been end-to-end verified. External certificate provisioning, service installation/rotation, and production operations still need deployment evidence. |
| Platform builds | Flutter package has Windows and Android runner scaffolding. Release builds target both platforms. Core and Host remain separate Dart packages with database/filesystem abstractions rather than Flutter or OS-specific dependencies in Core. | Android was exercised on an API 37 x86_64 emulator, not physical Android hardware. This does not establish hardware-specific behavior or production key-storage evidence. |

The Windows development machine has no persistent Host database configured; the local package/record integration used a temporary disposable PostgreSQL container.

The PostgreSQL integration run exposed test-fixture issues, which were corrected without relaxing Host checks: the direct scoped SQL fixture now supplies its trusted module ID, retry receipts are compared by canonical JSON content, and each test command has a unique idempotency ID. The Windows integration test creates recovery files in an ACL-protected per-run directory rather than relying on the broadly inherited ACL of the Windows temporary directory. It also proves operational roles cannot use the isolated HMAC schema, rejects proof replay/forgery, quarantines after an out-of-band role-permission edit with the installed recovery triggers active, prevents decrementing recovery generation, and rejects truncation. All eight GitHub Actions workflows passed for source commit `7f31ad7`, including PostgreSQL 16 package/record and RLS integrations, recovery and engineering gates, and Windows/Android client CI builds. More recent Actions attempts for the development branch have repeatedly failed before executing any job steps. Some job records show `runner_id` zero; the latest runs have no steps or log links. Retries show the same condition, so current CI has not evaluated the branch. Local Windows, Android, Flutter, API, Windows ACL, and PostgreSQL integration results above are independent evidence.

No physical Android hardware run, full interactive Windows UI acceptance session, or Windows Host serving clients on a LAN is claimed here. The Android emulator run validates the device-local Builder and record lifecycle only. Local UI widget tests and successful native builds are not substitutes for Host-backed and hardware checks.

## Remaining production gates

- Complete a real Windows Host deployment with PostgreSQL, protected recovery-authority provisioning, certificates, and remote Windows/Android credential enrollment.
- Run the cross-device acceptance scenario through a live Host: approve the locally demonstrated distinct extensions, synchronize actual records, exercise conflict/rejection and an extension upgrade without data loss, then verify on a second device.
- Exercise the Windows UI manually and install/run the APK on physical Android hardware.
- Validate the complete conflict/rejection lifecycle against a live multi-device Host, including concurrent edits that advance the Host revision during user review. Reviewed resumable migrations for changes beyond the supported additive schema subset are still needed.
- Add workload evidence and indexes for large Host/local datasets; current query bounds protect request size, but do not make an enterprise-scale latency guarantee.
- Production recovery still requires rollback protection outside the shared database and witness rollback domain. Matching rollback of both artifacts cannot be detected by the current local freshness design.

This status describes the current implementation slice and does not declare production readiness.
