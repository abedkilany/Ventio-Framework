# Recovery Authority coordinated Host upgrade

## Status

The 0.1.12 recovery-fingerprint failure is corrected in 0.1.13. A separate 0.1.13 backup failure was reproduced on Windows with a field-sized data tree and corrected in 0.1.14. A later 0.1.14 failure caused by VentioHost SCM recovery restarts racing the upgrade stop checks is corrected in 0.1.15. The physical Host and its live PostgreSQL cluster were not accessed or changed. Physical acceptance remains open.

## 0.1.14 service recovery race and correction

The 0.1.14 installer verifies the VentioHost identity and stopped state before backup, and the Recovery Authority helper checks again before its protected service start. It stopped VentioHost but left the service's Windows SCM failure actions active. If an earlier service failure had a delayed automatic restart pending, SCM could restart the Host after the installer observed `Stopped`; the first check would then fail before a schema-upgrade request was created. A second state check guards the deliberate Recovery Authority service start. That check now has its own safe stage, and the request is created only after the maintenance precondition succeeds. The exact stage is written beside the safe failure code and shown by Setup.

Setup 0.1.15 now uses a bounded service maintenance hold. After validating the existing `NT SERVICE\\VentioHost` account and executable path, it snapshots the exact SCM failure-action policy and failure-actions flag into a LocalMachine-DPAPI-protected record under `%ProgramData%\\Ventio\\Installer`. The record's DACL is limited to SYSTEM and Administrators, accepting the already-provisioned owner ACE on the protected installer directory. The installer temporarily disables recovery actions, stops VentioHost, and waits through the longest configured restart delay, stopping any already-queued restart and restarting the quiet window when one appears. It fails closed on unsupported reboot/run-command actions or a recovery delay longer than five minutes. It verifies the policy is still suppressed at both upgrade preconditions.

The installer restores and verifies the exact original reset period, recovery actions and delays, reboot message, command, and non-crash failure flag after the final Host readiness check. Handled failures restore the policy while leaving the Host stopped when the database upgrade failed. The protected record remains if restoration or verification fails; a subsequent Setup attempt reconciles it without changing service identity or database authority. If Setup is force-terminated or Windows loses power before cleanup, recovery actions remain suppressed and the Host must be left stopped until Setup 0.1.15 is rerun to reconcile the protected record. Recovery policy changes do not alter PostgreSQL, Recovery Authority, or Host authorization. Do not edit or delete the protected record manually.

Regression coverage includes a deterministic SCM-delay simulation reproducing the stopped-then-restarted race, checks of both upgrade failure stages and recovery preconditions, and an optional real SCM test that creates a disposable failing Windows service with staged restart delays and verifies policy suppression, drain, and exact restoration. The real SCM test requires an elevated test shell; it was BLOCKED in the current non-elevated development session. No test changed the installed Ventio Host or any physical Host state.

## 0.1.13 backup failure and correction

The reported `HOST_LAN_SETUP_FAILED_SERVICE_START` is generated by the LAN-listener service-start handler, not by the database backup routine. In the installer flow, a nonzero database-upgrade result exits before the LAN-listener stage, so that code does not identify the backup failure and may refer to a separate or earlier attempt. Version 0.1.13 did not persist or surface the database helper's backup-stage failure code.

The 0.1.13 backup sequence created and restricted the `.partial` directory, copied data with Robocopy `/COPY:DAT` and `/DCOPY:DAT`, compared file count and total bytes, then applied a second NTFS ACL rewrite to the already-populated `data` directory before writing the manifest. The data directory already had its intended restricted ACL before Robocopy. Robocopy's DAT flags intentionally do not copy source ACLs, so copied entries inherit the destination's protected ACL. The post-copy ACL rewrite was redundant and could fail with Windows `0x80070005` while propagating permissions over the populated tree. Since the manifest follows that rewrite, this failure leaves a complete `.partial` copy without a manifest.

This failure was reproduced in an isolated Windows fixture containing exactly 1,375 files and 50,810,225 bytes. Robocopy returned exit code 1 (a successful copy), the source/destination inventory matched, and the post-copy `Set-Acl` operation failed with `0x80070005` before manifest creation. The field partial has the same file count and byte size. The physical Host's live source count was collected while `VentioPostgres` was running, after the failed backup path had restarted PostgreSQL; the stable backup snapshot is taken while PostgreSQL is stopped, so its four fewer files and 515,612 fewer bytes do not establish an inventory mismatch. The source's extra `NT SERVICE\\VentioPostgres` FullControl ACE is intentional for the live database. Backup ACLs intentionally grant FullControl only to SYSTEM and Administrators; Robocopy's selected flags do not copy that service ACE.

Robocopy exit codes 0–7 remain accepted as success; 8 or higher indicates failure. The old helper discarded the actual code and did not persist source/backup inventory details. Version 0.1.14 now records a safe failure code and stage for Robocopy, inventory, NTFS ACL verification, manifest write, and finalization. It secures the destination before copying, verifies the resulting ACL without rewriting the populated directory, and verifies existing backup-directory ACLs without changing prior backups. `.partial` evidence remains intact on failure.

The corrected installer does not require restoring the previously verified pre-migration backup solely to recover from this backup-only failure: the failure occurs before the database migration request and leaves the live database and witness unchanged. Preserve the physical Host database, Recovery Authority witness, TLS configuration, verified backups, and `.partial` directory. Do not retry the upgrade until the corrected 0.1.14 package is available and verified. If the Host still has the separate stale-witness state caused by a previously committed 0.1.12 migration, the earlier stale-witness restore procedure below remains necessary.

The corrected 0.1.13 backup package was `dist/windows/0.1.14-backup-fix-final/Ventio-Setup-0.1.14.exe` (104,182,169 bytes), SHA-256 `85f046972b68b9150f7b70f54532f2faed5033c99e4fb4b33b32e71aec2f66f8`. The 0.1.14 recovery-action race is corrected in Setup 0.1.15; use the 0.1.15 artifact and checksum reported with the corresponding source commit. Locally built installers are not Authenticode-signed; verify the relevant SHA-256 against the value delivered through the trusted engineering channel before running one.

## Confirmed failure mechanism

The Host recovery fingerprint includes the ordered `ventio_schema_migrations` ledger. The 0.1.12 installer migration path applied migrations 031 and 032 directly, then updated SQL security contracts without coordinating the independent Recovery Authority witness. Those migrations advance the database fingerprint while the witness remains at its prior fingerprint. `ventio_security.admit_recovery()` correctly rejects that mismatch with SQLSTATE `28000`; this is the field-reported `ServerException`, not a PostgreSQL password or SCRAM failure.

The regression fixture starts from a migration-030 Host database, bootstraps a first administrator through the actual Recovery Authority flow, and persists its user, device, and credential before cloning the database. Applying 031 and 032 through the old direct migration path reproduces the mismatched fingerprints and `28000` denial.

## Upgrade transition

Production Host upgrades now pass through the existing Host Windows service identity and Recovery Authority. The installer first creates and verifies a restricted PostgreSQL data backup. It then enables one bounded PostgreSQL prepared transaction slot (`max_prepared_transactions = 1`) and verifies the running setting. It does not edit the Recovery Authority witness directly.

The trusted upgrade helper applies only the release-bundled migration batch inside a uniquely named PostgreSQL prepared transaction. The batch includes a durable receipt containing the operation id, old and new database fingerprints, and migration-manifest hash. It contains no identity or credential material.

The transition uses these durable states:

1. The independent witness records a pending `prepared` operation and its prior fingerprint.
2. PostgreSQL prepares the migration transaction. Changes and the receipt remain invisible until commit.
3. The independent witness records `commit_authorized` for that exact operation.
4. The Host commits the prepared transaction, verifies the exact receipt and resulting fingerprint, then finalizes the witness.

After a restart, an operation still in `prepared` has not been authorized to commit. A matching prepared transaction is rolled back, the unchanged prior fingerprint is verified, and the same operation can be retried. An operation in `commit_authorized` is completed by committing the matching prepared transaction or reconciled from its exact committed receipt. If the authorized transaction and its receipt are both missing, the Host stays quarantined; it never adopts an unproven database state.

This is a narrow two-phase transition for vetted schema upgrades, not a general remote transaction API. PostgreSQL documents prepared transactions as a mechanism for an external transaction manager and warns that they must be closed promptly; the Host helper owns and reconciles its uniquely identified operation. See the [PostgreSQL 16 `PREPARE TRANSACTION` reference](https://www.postgresql.org/docs/16/sql-prepare-transaction.html).

## Database and installation impact

- Migration 033 adds `public.host_schema_upgrade_receipts`. It stores only schema-upgrade evidence.
- Fresh bootstrap and the reviewed schema profile set the receipt table owner to `ventio_owner`, enable and force RLS, add an owner-only policy, and revoke access from runtime and identity API roles.
- Existing migrations 001–032 and all existing identity, device, credential, record, and audit rows remain in place.
- The installer backs up the cluster before adding the PostgreSQL setting or applying migrations. The existing service identity remains `NT SERVICE\VentioPostgres`; the Host service performs the upgrade as `NT SERVICE\VentioHost` through its protected request file and bundled helper.
- TLS certificate and Recovery Authority files are outside the PostgreSQL restore path and remain untouched. Client SQLite databases and their pending queues are not accessed by the Host installer.
- An old or mismatched witness is never overwritten, regenerated, or bypassed. Database rollback after a finalized upgrade remains rejected by Recovery Authority admission.

If there is any uncertainty about whether the live cluster still has a stale witness or which backup is the pre-migration one, stop and preserve the machine for support review. Setup 0.1.15 preserves any prior service recovery policy snapshot and restores it after the upgrade or on a handled failure.
2. Open an elevated PowerShell window. Confirm `VentioHost` is stopped. Run the recovery script bundled at `C:\Program Files\Ventio\host-payload\setup\restore-host-upgrade-backup.ps1` with the exact original pre-migration backup directory:

   ```powershell
   Stop-Service -Name VentioHost -Force
   & 'C:\Program Files\Ventio\host-payload\setup\restore-host-upgrade-backup.ps1' `
     -BackupDirectory 'C:\ProgramData\Ventio\Backups\ventio-postgresql-before-upgrade-<original timestamp and id>' `

   ```

   The script validates the restricted backup manifest and data inventory, preserves a second copy of the current failed cluster, restores the selected cluster through a same-volume directory swap, starts PostgreSQL, and leaves `VentioHost` stopped. 3. Run the same Ventio Setup 0.1.14 package again. It will create a fresh verified backup, coordinate migrations 031–033 with the independent witness, apply the reviewed security contracts, and start the Host only after contract verification.
4. Verify Host Readiness reports API, Database, Schema, and Recovery Authority READY. Verify the original Client still presents the same device identity and its local records and pending command ids remain present. Then exercise normal Host-authoritative synchronization.

If Setup reports `HOST_SCHEMA_UPGRADE_OUTCOME_UNKNOWN`, `HOST_SCHEMA_UPGRADE_RECOVERY_ADMISSION`, or leaves `VentioHost` stopped, do not restore another backup or edit the witness. Preserve the operation result and both verified backup directories and escalate for controlled reconciliation.

## Ventio Setup 0.1.15 pre-install failure diagnosis and 0.1.16 correction

An elevated Windows PowerShell 5.1 reproduction identified the first failing operation as DPAPI protection while creating the SCM recovery-policy journal. Windows PowerShell 5.1 did not auto-load the .NET Framework assembly containing `System.Security.Cryptography.ProtectedData`; journal creation therefore failed before the file was committed. The stop helper attempted a safe rollback, found no journal to restore, and exited before Setup replaced application files. The physical evidence of an absent journal is consistent with this failure. Folder ownership and explicit Administrators/SYSTEM ACLs were not the cause.

The same real SCM lifecycle test exposed two later defects which the pre-journal failure had masked: Windows PowerShell 5.1's empty-array semantics could pass a null action array to the suppression path, and a service handle restoring `SC_ACTION_RESTART` must also include `SERVICE_START`. The correction loads `System.Security` explicitly, uses one explicit `SC_ACTION_NONE` entry for temporary suppression, and requests only `SERVICE_CHANGE_CONFIG` plus `SERVICE_START` when restoring restart actions. During maintenance, restart draining remains bounded by the longest configured delay and verifies the Host remains stopped.

The pre-install helper now writes only allow-listed symbolic `Code=` and `Stage=` values to a temporary diagnostic file; it does not include exception text, tokens, command contents, or service-policy details. Setup validates those fields before displaying them. Useful stages include `RECOVERY_JOURNAL_DPAPI_PROTECT`, `RECOVERY_JOURNAL_DIRECTORY_ACL_VALIDATE`, `SERVICE_RECOVERY_POLICY_SUPPRESS`, `SERVICE_RECOVERY_POLICY_RESTORE`, and `SERVICE_RESTART_DRAIN`.

The corrected Windows installer is `dist/windows/0.1.16-ps51-preinstall-fix-final/Ventio-Setup-0.1.16.exe`, SHA-256 `a67288c2865cddeb9ca188614c4f636c2e43fe1ad1db842738696d387c34bc5f`. Verify it against the adjacent SHA-256 manifest before running it as Administrator. This package is currently unsigned. Do not restore the PostgreSQL database, regenerate or modify Recovery Authority, remove backups, or edit an installer journal because of the earlier PrepareToInstall failure. ## Ventio Setup 0.1.16 coordinated-migration failure and 0.1.17 diagnostics

The 0.1.16 failure label `HOST_DATABASE_UPGRADE_FAILED` at `DATABASE_COORDINATED_MIGRATION` is too broad to prove which operation failed. That stage includes configuration file read/write/replace, PostgreSQL restart and readiness, prepared-transaction and migrator-profile preflight, trusted Host migration, Recovery Authority admission, SQL contract application, contract verification, and migration-ledger verification. Missing request/result files after the event do not identify the failing step because a later attempt or cleanup may remove them.

The stale-witness condition was reproduced on an isolated Windows PostgreSQL 16.15 cluster from an existing migration-030 database with a persisted first administrator, device, and credential. The reproduction committed migrations 031 and 032 without advancing the copied independent witness. The database and witness fingerprints then disagreed; `ventio_security.admit_recovery()` returned SQLSTATE `28000`. Running the trusted upgrade helper against that migration-032 database failed at Recovery Authority fingerprint preflight, before migration 033 or security-contract mutation. The ledger remained at 32 entries; user, device, and credential row counts and IDs remained unchanged; and the witness remained unchanged. The normal coordinated migration path with a matching witness passed and preserved those same rows. This demonstrates the stale witness as a sufficient explanation for the failure shape; the 0.1.16 physical event cannot be attributed to that operation conclusively because 0.1.16 did not record its nested stage.

Setup 0.1.17 now records a safe operation stage for each step inside `DATABASE_COORDINATED_MIGRATION`. The fixed Host helper includes an allow-listed failure stage in its local result so Setup can report the inner migration/preflight operation. Before starting the coordinated mutation, the helper also performs a read-only fingerprint comparison. A mismatch returns `HOST_SCHEMA_UPGRADE_RECOVERY_FINGERPRINT_MISMATCH` at `TRUSTED_HOST_UPGRADE_RECOVERY_AUTHORITY_FINGERPRINT_PREFLIGHT`. It does not print either fingerprint, change the witness, alter the migration ledger, or bypass the prepared-transaction protocol. Pending witness state still goes through the existing operation-id and receipt reconciliation path.
