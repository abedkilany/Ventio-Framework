# Native Flutter Client — Phase 1: Foundation and Durable Local Queue

## Scope

This phase adds a separate Flutter app at `packages/ventio_native_client` for Windows and Android. It does not move or reuse the original Ventio application. The sample UI creates Maintenance Requests only.

The app reuses `ventio_core` `CommandEnvelope` values and the shared v0 command envelope JSON. Core also exposes `CommandReceipt.fromJson` so a future transport can parse Host receipts without defining a second receipt contract. The Host HTTP wrapper is not part of the Core receipt; a future transport must unwrap `apiVersion` and `receipt` first.

## Durable local behavior

- SQLite stores the original immutable Core envelope and stable command ID in one transaction.
- The database has a unique primary key on command ID. Enqueue checks for an existing ID and never replaces its original intent.
- The local `host_status` starts at `PENDING`. The accepted, rejected, conflict, and retry states require a separate Host receipt in the schema.
- The transport fixture writes only `fixture_receipt_json`. It cannot write `host_receipt_json` or change `host_status`.
- SQLite is configured for WAL and `synchronous=FULL`; attempt metadata and fixture output are committed transactionally.
- The UI labels every local request Pending and explains that the fixture response is simulated.
- Demo tenant/user/device identifiers are placeholders. No identity credentials are stored or sent.

There is no Host transport implementation, authenticated sync, snapshot, confirmed projection, or Host acceptance in this phase. No network listener, proxy, tunnel, LAN binding, or external API exposure is added.

## Platform setup and commands

The app's Dart source and dependency configuration are committed. Standard Android and Windows runner files are generated by the pinned Flutter SDK, avoiding a second hand-maintained copy of Flutter's platform templates.

On Windows PowerShell:

```powershell
.\scripts\prepare_native_client_platforms.ps1
cd packages\ventio_native_client
flutter pub get
flutter analyze
flutter test
flutter build windows --debug
```

On Linux, use `./scripts/prepare_native_client_platforms.sh` and run `flutter pub get`, `flutter analyze`, and `flutter test` from the client directory. Windows builds require Windows with Visual Studio desktop C++ tools. Android APK builds can run on Linux with the Android SDK installed.

## Test boundaries

`flutter test` uses SQLite FFI and covers Core contract compatibility, exact envelope rehydration, close/reopen durability, duplicate-ID rejection without overwrite, interruption after attempt recording, fixture-receipt persistence, fixture/Host state separation, and the Maintenance form's Pending state.

The CI workflow uses Flutter 3.47.0 and has independent jobs for queue/contract tests, Windows build, and Android debug APK build. These builds do not prove emulator/physical-device installation or launch. The execution workspace used to prepare this change has no Flutter or Dart SDK, so local Flutter compilation and test execution were unavailable; CI is the required compiler/runtime verification. No actual process-kill, Android emulator, Windows interactive launch, or Host-to-client transport test is claimed.

## Next proof boundary

The next approved slices can add crash-boundary process tests, reviewed Windows/Android secure credential storage, a real confirmed-state projection, and a transport/deployment design under a separate security gate. The existing Linux Host remains loopback-only until that gate is explicitly approved.
